## 一、必背清单

### 模块 A ｜ 架构设计（5.1.1）

- [ ] **A0 · 软件架构研究的四方面内容与根本目的** ⭕ 必背（原句挖空）
  软件架构研究的主要内容涉及**软件架构描述、软件架构风格、软件架构评估和软件架构的形式化方法**等。解决好软件的**复用、质量和维护**问题，是研究软件架构的根本目的。
  - 软件架构设计的一个**核心问题**是能否达到**架构级的软件复用**
  > 记法：研究内容四件套「**描述 · 风格 · 评估 · 形式化**」；根本目的「**复质维**（复用 / 质量 / 维护）」
- [ ] **A1 · 五大架构风格及子风格** ⭕ 必背（风格归属题年年考）
  | 风格 | 子风格 | 关键词 |
  |---|---|---|
  | **数据流风格** | **批处理序列**、**管道/过滤器** | 顺序执行 / 输入输出数据流 |
  | **调用/返回风格** | **主程序/子程序**、**数据抽象和面向对象**、**层次结构** | 过程调用 / 对象及封装 / 分层调用 |
  | **独立构件风格** | **进程通信**、**事件驱动**的系统 | 消息传递 / 事件触发调用 |
  | **虚拟机风格** | **解释器**、**基于规则**的系统 | 解释引擎 / 规则集 |
  | **仓库风格** | **数据库系统**、**黑板系统**、**超文本系统** | 中央共享数据源 / 知识源+黑板 / 非线性交叉引用 |
  - 管道/过滤器风格：输出的正确性**不依赖于过滤器执行（增量计算）的顺序**
  - 面向对象（数据抽象）风格的缺点：对象之间调用需要**知道所调用对象的标识**，标识改变须通知所有调用者
  > 口诀：**数调独虚仓**。高频对位：「批处理序列」属**数据流**、「层次结构」属**调用/返回**、「事件驱动」属**独立构件**、「解释器」属**虚拟机**、「黑板系统」属**仓库**
- [ ] **A2 · 架构评估：敏感点与权衡点** ⭕ 必背（最高频辨析）
  在架构评估过程中，评估人员所关注的是系统的**质量属性**。
  - **敏感点**：是一个或多个构件（部件）的特性，影响**单个（某一）质量属性**
  - **权衡点**：是影响**多个质量属性**的特性，是**多个质量属性的敏感点**（如加密级别越高安全性越好、性能越差）
  > 记法：**敏感点管一个，权衡点管一串**；「影响多个质量属性」→ 必答权衡点
- [ ] **A3 · 三类架构评估方式与场景法三工具** ⭕ 必背
  从目前已有的软件架构评估技术来看，可归纳为三类主要评估方式：基于**调查问卷（或检查表）**的方式、基于**场景**的方式和基于**度量**的方式。其中**基于场景的评估方式最为常用**。
  - 基于场景的方式主要包括：**架构权衡分析法（ATAM）**、**软件架构分析法（SAAM）**、**成本效益分析法（CBAM）**
  > 记法：问卷 / 场景 / 度量三类，**场景最常用**；场景三法「**ATAM 权衡 · SAAM 分析 · CBAM 成本**」

### 模块 B ｜ 需求分析（5.1.2）

- [ ] **B0 · 软件需求定义与三个层次** ⭕ 必背（层次归属）
  **软件需求**是指用户解决问题或达到目标所需的条件或能力，是系统或系统部件要满足合同、标准、规范或其他正式规定文档所需具有的条件或能力。需求是多层次的：
  | 层次 | 定义 | 关键词 |
  |---|---|---|
  | **业务需求** | 反映企业或客户对系统**高层次**的目标追求 | 来自投资人 / 客户 / 管理人员 / 市场或产品策划部门 |
  | **用户需求** | 描述**用户的具体目标**，或用户要求系统必须能完成的任务 | 用户能让系统**做什么** |
  | **系统需求** | 从**系统的角度**说明软件的需求 | 包括**功能需求、非功能需求和设计约束** |
  > 记法：三层次从**目标到具体、从整体到局部、从概念到细节**；「高层次目标」=业务需求、「用户的具体目标」=用户需求、「功能+非功能+设计约束」=系统需求
- [ ] **B1 · QFD 与三类需求（常规 / 期望 / 意外）** ⭕ 必考（判别关键词挖空）
  **质量功能部署（QFD）**是一种将用户要求转化成软件需求的技术，其目的是**最大限度地提升软件工程过程中用户的满意度**。QFD 将软件需求分为三类：
  | 类型 | 判别关键词 |
  |---|---|
  | **常规需求** | 用户认为系统**应该实现**的功能或性能，**实现得越多用户会越满意** |
  | **期望需求** | 用户**想当然**以为系统应具备的功能或性能，但**不能正确描述**；若没有实现，会让用户**不满意** |
  | **意外需求** | 也称**兴奋需求**，是用户要求**范围之外**的功能或性能 |
  > 记法：常规「越实现越满意」/ 期望「想当然、不实现就不满意」/ 意外「兴奋需求、范围外」
- [ ] **B2 · 需求过程四环节与需求获取方法** ⭕ 必背
  需求过程主要包括**需求获取、需求分析、需求规格说明书编制、需求验证与确认**。
  - **需求获取**：是一个确定和理解不同的**项目干系人的需求和约束**的过程。常见获取方法：**用户访谈、问卷调查、采样、情节串联板、联合需求计划**等
  > 记法：四环节「**获取 → 分析 → 编制 → 验证确认**」；获取方法五件「**访问采串联**」
- [ ] **B3 · 好需求的八个特性** ⭕ 常考（多选 / 判断）
  一个好的需求应该具有**无二义性、完整性、一致性、可测试性、确定性、可跟踪性、正确性、必要性**等特性。需求分析人员需要把杂乱无章的用户要求和期望转化为（好的）用户需求。
  > 记法：「**无完一测确跟正必**」；注意**没有「可扩展性」「经济性」**这类干扰项
- [ ] **B4 · 结构化分析（SA）三模型** ⭕ 必背（模型⇄图形配对，年年考）
  使用**结构化分析（SA）**方法进行需求分析，其建立的模型的**核心是数据字典**。围绕这个核心，有三个层次的模型：
  | 模型 | 图形 | 描述内容 |
  |---|---|---|
  | **数据模型** | **实体关系图（E-R 图）** | 实体、属性以及实体之间的关系 |
  | **功能模型** | **数据流图（DFD）** | 数据传递和加工，逐层细分描述系统功能与数据流向 |
  | **行为模型**（状态模型） | **状态转换图（STD）** | 系统的状态和引起状态转换的事件，表示系统行为 |
  > 口诀：**核心是数据字典（不是 DFD！）**；「**数 E-R · 功 DFD · 行 STD**」三对配对别接错
- [ ] **B5 · 面向对象分析（OOA）与用例模型四阶段** ⭕ 必背
  **面向对象分析（OOA）**的模型包括**用例模型和分析模型**。构建用例模型一般需要四个阶段：
  1. **识别参与者**（必须）
  2. **合并需求获得用例**（必须）
  3. **细化用例描述**（必须）
  4. **调整用例模型**
  > 记法：OOA 两模型「**用例 + 分析**」；四阶段「**识参与 → 并需求 → 细描述 → 调模型**」
- [ ] **B6 · 软件需求规格说明书（SRS）** ⭕ 常考
  **SRS 是需求开发活动的产物**，是软件开发过程中**最重要的文档之一**，对于任何规模和性质的软件项目都**不应该缺少**。编制 SRS 的目的是使项目干系人与开发团队对系统的初始规定有一个**共同的理解**，使之成为整个开发工作的**基础**。
  - **需求评审**就是对 SRS 进行**技术评审**
  > 记法：SRS = 需求开发产物 =「共同理解 + 开发基础」；评审对象是 SRS
- [ ] **B7 · UML：事物四类 / 关系四类 / 14 图 / 5 视图** ⭕ 必背（UML 是 5.1.2 的压轴考点）
  - **UML 中的事物**（建模元素）包括：**结构事物、行为事物、分组事物和注释事物**
  - **UML 中的关系**四类：
    | 关系 | 定义关键词 |
    |---|---|
    | **依赖** | 一个事物发生变化会影响**另一个事物的语义** |
    | **关联** | 描述一组对象之间**链接的结构关系** |
    | **泛化** | **一般化和特殊化**的关系，特殊元素对象可替换一般元素对象 |
    | **实现** | 类之间的语义关系，一个类制定由另一个类**保证执行的契约** |
  - **UML 2.0 的 14 种图**：类图、对象图、构件图、组合结构图、用例图、顺序图、通信图、定时图、状态图、活动图、部署图、制品图、包图、交互概览图
    - 常考对位：**顺序图强调消息的时间次序**；**通信图（协作图）强调收发消息对象的组织结构**；**状态图描述对象生命周期**；**活动图本质是流程图**；**部署图描述软件到硬件的映射**
  - **UML 视图**（5 种）：**逻辑视图**（也称设计视图）、**进程视图**（可执行线程和进程的建模，逻辑视图的一次执行实例）、**实现视图**（物理代码的文件和构件建模）、**部署视图**（构件部署到物理节点，软件到硬件的映射）、**用例视图**（**最基本的需求分析模型**）
  > 记法：事物「**结行分注**」/ 关系「**依关泛实**」；⚠️ **UML 五视图 ≠ 架构师考试的「4+1 视图」**——教材口径是逻辑 / 进程 / 实现 / 部署 / 用例；「**用例视图是最基本的需求分析模型**」是原句考点

### 模块 C ｜ 软件设计（5.1.3）

- [ ] **C0 · 结构化设计（SD）** ⭕ 必背
  **结构化设计（SD）**是一种**面向数据流**的方法，它以 SRS 和 SA 阶段所产生的 **DFD 和数据字典**等文档为基础，是一个**自顶向下、逐步求精和模块化**的过程。SD 分为**概要设计（又称总体结构设计）**和**详细设计**两个阶段，需要遵循一个基本原则：**高内聚、低耦合**。
  > 记法：SD 三特征「**顶向精模**（自顶向下 / 逐步求精 / 模块化）」+ 原则「**高内聚低耦合**」+ 两阶段「概要=总体结构设计 / 详细」
- [ ] **C1 · 面向对象设计（OOD）：基本思想与三大特征** ⭕ 必背
  **OOD 是 OOA 方法的延续**，其基本思想包括**抽象、封装和可扩展性**，其中**可扩展性主要通过继承和多态来实现**。
  - 面向对象的**三大特征**：**封装、继承、多态**
  > 记法：基本思想三件「**抽封扩**」；可扩展性 = 继承 + 多态
- [ ] **C2 · 面向对象设计的七大原则** ⭕ 常考（名称识别）
  | 原则 | 一句话 |
  |---|---|
  | **单一职责原则** | 一个类只负责一项职责 |
  | **开闭原则** | 对扩展开放，对修改关闭 |
  | **里氏替换原则** | 父类能出现的地方子类必能替换 |
  | **依赖倒置原则** | 依赖抽象（接口），不依赖具体实现 |
  | **接口隔离原则** | 接口小而专，不强迫依赖无用方法 |
  | **组合重用原则** | 多用组合，少用继承 |
  | **迪米特原则** | 最少知识原则（别和「陌生人」说话） |
  > 口诀：**单开里依接组迪**
- [ ] **C3 · 设计模式：两类范围 + 三种用途** ⭕ 必背
  设计模式是前人经验的总结，使人们可以方便地**复用成功的软件设计**。按**处理范围**不同分为**类模式和对象模式**；按**目的和用途**不同分为三种：
  | 类型 | 用途 | 代表模式 |
  |---|---|---|
  | **创建型模式** | 主要用于**创建对象** | 工厂方法、抽象工厂、原型、单例、建造者 |
  | **结构型模式** | 处理**类或对象的组合** | 适配器、桥接、组合、装饰、外观、享元、代理 |
  | **行为型模式** | 描述**类或对象的交互以及职责分配** | 职责链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者 |
  > 记法：**创建建对象 · 结构管组合 · 行为交互职责**；单例=创建型、代理=结构型、观察者=行为型是高频对位

### 模块 D ｜ 软件实现（5.1.4）

- [ ] **D0 · 软件配置管理六项** ⭕ 常考
  软件配置管理包括：**软件配置管理计划、软件配置标识、软件配置控制、软件配置状态记录、软件配置审计、软件分布（发布）管理与交付**。
  > 记法：「**计划标识控制 · 记录审计交付**」六件套
- [ ] **D1 · 软件编码三个关注点** ⭕ 通读
  将设计转化为程序代码，关注：**程序设计语言的选择**、**程序设计风格**（源程序文档化、数据说明、语句结构、输入/输出）、**编码效率**（程序执行速度、内存占用、存储效率、I/O 效率）。
- [ ] **D2 · 软件测试目的与静态测试** ⭕ 必背
  软件测试的目的是**验证软件是否满足**软件开发合同或项目开发计划、系统/子系统设计文档、SRS、软件设计说明和软件产品说明等**规定的软件质量要求**。
  - **静态测试**：采用**人工检测**和**计算机辅助静态分析**的手段对程序进行检测，**不实际运行程序**；包括对文档和代码的静态测试——对文档主要以**检查单**的方式，对代码主要是**桌前检查、代码走查和代码审查**
  - 静态测试可以发现约 **30% ~ 70%** 的逻辑设计和编码错误
  > 记法：静态测试代码三手段「**桌走审**（桌前检查 / 代码走查 / 代码审查）」、文档用「检查单」
- [ ] **D3 · 动态测试：白盒 vs 黑盒** ⭕ 必背（别名 / 阶段 / 方法三线全对上是得分点）
  | 维度 | 白盒测试 | 黑盒测试 |
  |---|---|---|
  | 别名 | **结构测试** | **功能测试** |
  | 视角 | 了解程序**内部结构和处理算法**，覆盖逻辑通路 | 只检查程序功能**能否按 SRS 要求正常使用** |
  | 主要用于 | **单元测试** | **集成测试、确认测试和系统测试** |
  | 常用方法 | 控制流测试、数据流测试、程序编译测试；最常用技术是**逻辑覆盖**（语句/判定/条件/路径覆盖） | **等价类划分、边界值分析、判定表、因果图、状态图、随机测试、猜错法、正交试验法** |
  > 记法：**白盒单元逻辑覆盖 · 黑盒集成确认系统等价边界**；「逻辑覆盖」属白盒，「等价类划分」属黑盒，高频对调坑

### 模块 E ｜ 部署交付（5.1.5）

- [ ] **E0 · 软件部署与交付的定义** ⭕ 常考
  软件部署与交付是软件生命周期中的一个**重要环节**，属于软件开发的**后期活动**，即通过**配置、安装和激活**等活动来保障软件制品的后续运行。
  > 记法：三个动词「**配装激**（配置 / 安装 / 激活）」；「后期活动」
- [ ] **E1 · 持续交付** ⭕ 必背
  **持续交付**是一系列开发实践方法，用来确保让代码能够**快速、安全地部署到生产环境**中。持续交付是一个**完全自动化的过程**，当业务开发完成时，可以做到**一键部署**。
  - 持续交付对传统流程的改进方案：
    | 阶段 | 做法 |
    |---|---|
    | 需求阶段 | 抛弃传统需求文档，使用便于开发人员理解的**用户故事** |
    | 开发测试阶段 | 做到**持续集成**，让测试人员尽早进入项目开始测试 |
    | 运维阶段 | **打通开发和运维之间的通路**，保持开发环境和运维环境的**统一** |
  - 优势：有效缩短提交代码到正式部署上线的时间、降低部署风险；自动快速提供反馈、及时发现修复缺陷；使软件在整个生命周期内**处于可部署状态**；简化部署步骤、版本清晰；使交付过程**可靠、可预期、可视化**
  > 记法：核心句「**完全自动化 + 一键部署**」；三阶段「需求用故事 · 开发持续集成 · 运维环境统一」
- [ ] **E2 · 持续部署与部署方案 / 原则 / 层次** ⭕ 常考
  - **容器技术**是目前部署中**最流行的技术**，常用的持续部署方案：**Kubernetes+Docker** 和 **Matrix** 两种
  - **部署层次**三个环节：**Build（编译形成 RPM 包或 Jar 包）→ Ship（第三方依赖和插件安装到环境）→ Run（在不同地方启动整套环境）**
  - **不可变服务器**：是一种**部署模式**，是指**除了更新和安装补丁程序以外，不对服务器进行任何更改**
  > 记法：容器=最流行；层次口诀「**B-S-R（构建-装载-运行）**」；不可变服务器=「只打补丁不改服务器」
- [ ] **E3 · 蓝绿部署 vs 金丝雀部署** ⭕ 必背（两者对调是高频坑）
  | 方式 | 做法 | 特点 |
  |---|---|---|
  | **蓝绿部署** | 准备**新旧两个部署版本**，通过**域名解析切换**的方式将用户环境切换到新版本 | 出问题可**快速切回旧版本**，并对新版本修复调整 |
  | **金丝雀部署** | 新版本发布时，先让**少量用户**使用新版本并观察是否存在问题 | 有问题及时处理并重新发布；正常则**稳步推广给所有用户**（灰度发布） |
  > 记法：**蓝绿=两套环境整体切换 · 金丝雀=小流量灰度验证**

### 模块 F ｜ 过程管理（5.1.6）

- [ ] **F0 · CSMM 模型的总体结构** ⭕ 必背（数字挖空）
  **CSMM（《软件过程能力成熟度模型》）**由 **4 个能力域、20 个能力子域、161 个能力要求**组成。
  > 记法：**4 域 / 20 子域 / 161 要求**——三个数字都能单独出题
- [ ] **F1 · CSMM 的四个能力域** ⭕ 必背（子域归属辨析）
  | 能力域 | 能力子域 | 落点 |
  |---|---|---|
  | **治理** | 战略与治理、目标管理 | 确定组织的**战略、产品方向、业务目标**并确保目标实现 |
  | **开发与交付** | 需求、设计、开发、测试、部署、服务、开源应用 | 通过软件工程过程**交付满足需求的软件**，为顾客与利益干系人**增加价值** |
  | **管理与支持** | 项目策划、项目监控、项目结项、质量保证、风险管理、配置管理、供应商管理 | 覆盖软件开发项目**全过程**，按既定**成本、进度和质量**交付 |
  | **组织管理** | 过程管理、人员能力管理、组织资源管理、过程能力管理 | 对软件**组织能力**进行综合管理 |
  > 记法：治理「战略目标」/ 开发交付「需求设计开发测试部署服务开源」/ 管理支持「策划监控结项 · 质保风险配置供应商」/ 组织管理「过程人员资源」
- [ ] **F2 · CSMM 的五个成熟度等级** ⭕ 必背（与 CMMI 别背串）
  | 等级 | 名称 | 特征关键词 |
  |---|---|---|
  | 1 | **初始级** | 过程和结果**不确定性** |
  | 2 | **项目规范级** | **基本可按计划**实现 |
  | 3 | **组织改进级** | 组织范围内能够**稳定**地实现预期目标 |
  | 4 | **量化提升级** | **量化**地管理和实现 |
  | 5 | **创新引领级** | **创新、持续提升、引领** |
  > 口诀：**初规组量引**。⚠️ CSMM 五级 ≠ CMMI 五级（初始 / 已管理 / 已定义 / 量化管理 / 优化）——第 2 级「项目规范级」、第 3 级「组织改进级」是 CSMM 独有叫法

## 二、通读补充（只看不背）

- [ ] **G0 · 管道/过滤器风格的优缺点** ○ 通读
  优点：体现功能模块「黑盒」特性、高内聚低耦合；支持软件功能模块重用；便于系统维护（新增/替换过滤器）；支持吞吐量计算、死锁检测等特定分析；支持并行操作。缺点：通常导致成批操作；需要协调两个相对独立又有关联的数据流；过滤器可能要自己完成数据解析合成，导致性能下降、实现复杂。
- [ ] **G1 · 事件驱动风格的特点** ○ 通读
  事件的触发者**并不知道**哪些构件会受到事件影响，也不能假定构件的处理顺序；典型应用是各种**图形界面工具（应用）**。
- [ ] **G2 · 面向对象模式的优缺点** ○ 通读
  优点：高度模块化、封装实现数据隐藏、继承实现代码共享、灵活便于维护扩充。缺点：对象间调用需知道对象标识，标识改变须通知所有调用者。
- [ ] **G3 · 部署与交付的新趋势** ○ 通读
  软件的部署与交付是一个持续不断的过程，伴随整个研发过程；发展趋势包括自动化程度不断提高、容器化 / 云化部署普及等。

## 三、易混防坑（考前再过一遍）

1. **敏感点 vs 权衡点**：敏感点影响**单个**质量属性；权衡点影响**多个**质量属性（=多个质量属性的敏感点）
2. **三类评估方式**：调查问卷（检查表）/ **场景（最常用）**/ 度量；ATAM、SAAM、CBAM 都是**基于场景**的方式
3. **架构风格归属**：批处理序列→数据流；层次结构→**调用/返回**（不是独立构件）；事件驱动→**独立构件**（不是虚拟机）；黑板系统→**仓库**；解释器→**虚拟机**
4. **SA 的核心是数据字典**（不是 DFD）；三模型配对「数据-E-R / 功能-DFD / 行为-STD」别对调
5. **QFD 三需求**：常规「越实现越满意」/ 期望「想当然，不实现会不满意」/ 意外「兴奋需求，范围外」——「想当然」= 期望需求
6. **UML 五视图**（逻辑/进程/实现/部署/用例）是教材口径；「用例视图是**最基本的需求分析模型**」；别与架构师考试的「4+1 视图」混
7. **白盒=结构测试=单元测试=逻辑覆盖**；**黑盒=功能测试=集成/确认/系统测试=等价类/边界值**——三线（别名/阶段/方法）要能同时对上
8. **静态测试**不运行程序（桌前检查/代码走查/代码审查），**静态测试方法也可以实现白盒测试**
9. **蓝绿部署**：新旧两版本+域名解析切换+快速回滚；**金丝雀部署**：少量用户先试+灰度推广——两者对调是高频坑
10. **CSMM ≠ CMMI**：CSMM 五级「初始 / 项目规范 / 组织改进 / 量化提升 / 创新引领」；CMMI 是「初始 / 已管理 / 已定义 / 量化管理 / 优化」；教材 5.1.6 讲的是 **CSMM**
11. **部署层次 Build→Ship→Run**：Build 编译出包、Ship 装依赖、Run 启动环境，顺序别乱
12. **结构化设计分两阶段**：概要设计（**又称总体结构设计**）+ 详细设计；「总体结构设计」就是概要设计的别称

## 四、自检问答（合上清单试着回答）

<details>
<summary>1. 研究软件架构的根本目的是什么？核心问题是什么？</summary>

解决好软件的**复用、质量和维护**问题是研究软件架构的根本目的；软件架构设计的一个核心问题是能否达到**架构级的软件复用**。
</details>

<details>
<summary>2. 五大架构风格各自的子风格有哪些？（每类至少说出 2 个）</summary>

数据流（批处理序列 / 管道-过滤器）；调用/返回（主程序-子程序 / 数据抽象和面向对象 / 层次结构）；独立构件（进程通信 / 事件驱动）；虚拟机（解释器 / 基于规则的系统）；仓库（数据库系统 / 黑板系统 / 超文本系统）。
</details>

<details>
<summary>3. 什么是敏感点？什么是权衡点？架构评估三类方式中最常用的是哪种？场景法包括哪三种？</summary>

敏感点 = 影响单个质量属性的构件特性；权衡点 = 影响多个质量属性的特性（多个质量属性的敏感点）。三类方式：调查问卷（检查表）/ 基于场景（**最常用**）/ 基于度量。场景法：ATAM（架构权衡分析法）/ SAAM（软件架构分析法）/ CBAM（成本效益分析法）。
</details>

<details>
<summary>4. 需求的三个层次是什么？QFD 把软件需求分为哪三类？判别关键词分别是什么？</summary>

业务需求（高层次目标）、用户需求（用户具体目标 / 用户让系统做什么）、系统需求（功能需求 + 非功能需求 + 设计约束）。QFD 三类：常规需求（应该实现，越实现越满意）、期望需求（想当然、不能正确描述，不实现会不满意）、意外需求（兴奋需求，范围之外）。
</details>

<details>
<summary>5. 需求过程四环节？常见需求获取方法五种？好需求的八个特性？</summary>

四环节：需求获取 → 需求分析 → 需求规格说明书编制 → 需求验证与确认。获取方法：用户访谈、问卷调查、采样、情节串联板、联合需求计划。八特性：无二义性、完整性、一致性、可测试性、确定性、可跟踪性、正确性、必要性。
</details>

<details>
<summary>6. SA 方法的核心是什么？三个层次的模型分别用什么图表示？</summary>

核心是**数据字典**。数据模型→实体关系图（E-R）；功能模型→数据流图（DFD）；行为模型→状态转换图（STD）。
</details>

<details>
<summary>7. OOA 构建用例模型的四个阶段？UML 的事物和关系各分四类是什么？</summary>

四阶段：识别参与者 → 合并需求获得用例 → 细化用例描述 → 调整用例模型。事物：结构事物、行为事物、分组事物、注释事物。关系：依赖、关联、泛化、实现。
</details>

<details>
<summary>8. UML 五视图是哪五个？哪个视图是最基本的需求分析模型？</summary>

逻辑视图（也称设计视图）、进程视图、实现视图、部署视图、用例视图；**用例视图是最基本的需求分析模型**。
</details>

<details>
<summary>9. 结构化设计的基本原则？分哪两个阶段？OOD 的基本思想和三大特征？七大原则口诀？</summary>

高内聚、低耦合；概要设计（总体结构设计）+ 详细设计。OOD 基本思想：抽象、封装、可扩展性（继承+多态）；三大特征：封装、继承、多态。七原则口诀：单开李依接组迪（单一职责 / 开闭 / 里氏替换 / 依赖倒置 / 接口隔离 / 组合重用 / 迪米特）。
</details>

<details>
<summary>10. 设计模式按用途分哪三类？各类用途和代表模式？</summary>

创建型（用于创建对象：工厂方法 / 抽象工厂 / 原型 / 单例 / 建造者）；结构型（处理类或对象的组合：适配器 / 桥接 / 组合 / 装饰 / 外观 / 享元 / 代理）；行为型（描述交互及职责分配：观察者 / 策略 / 命令 / 状态等 11 种）。
</details>

<details>
<summary>11. 白盒测试和黑盒测试的别名、用途、常用方法分别是什么？</summary>

白盒 = 结构测试，用于单元测试，最常用逻辑覆盖（另有控制流 / 数据流 / 程序编译测试）；黑盒 = 功能测试，用于集成、确认和系统测试，方法有等价类划分、边界值分析、判定表、因果图、状态图、随机测试、猜错法、正交试验法。
</details>

<details>
<summary>12. 持续交付和持续部署分别是什么？蓝绿部署和金丝雀部署的区别？CSMM 五个等级的名称？</summary>

持续交付：一系列开发实践方法，完全自动化、可一键部署、确保代码快速安全部署到生产环境。持续部署：在持续交付基础上自动化完成部署全过程（容器技术最流行：K8s+Docker / Matrix；build-ship-run 三环节）。蓝绿 = 新旧两版本域名解析整体切换、可快速回滚；金丝雀 = 少量用户先试、灰度推广。CSMM 五级：初始级、项目规范级、组织改进级、量化提升级、创新引领级。
</details>
