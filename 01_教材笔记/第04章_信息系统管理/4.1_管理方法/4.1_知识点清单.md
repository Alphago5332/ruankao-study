## 一、必背清单

### 模块 A ｜ 管理基础（4.1.1）

- [ ] **A0 · 信息系统的定义与四大要素** ⭕ 必背（定义题原句）
  **信息系统**是对信息进行**采集、处理、存储、管理和检索**，形成组织中的信息流动和处理，必要时能向有关人员提供有用信息的系统，它是由**人、技术、流程和数据资源**组成的人机系统。
  - **信息系统包括四个要素**：**人员**（使用者、管理者、开发者——系统的主导者）· **技术**（硬件、软件、网络——物理基础和工具）· **流程**（管理流程、业务流程——规定「如何做事」）· **数据**（信息载体、决策依据——系统加工的对象与核心价值）
  - 一句话记：**谁（人员）用什么（技术）按什么步骤（流程）处理什么（数据）**
  > 记法：定义抓五个动词「**采处存管检**」；四要素「**人技流数**」；注意是**四要素**，不是「人机一体化」「五大部件」
- [ ] **A1 · 信息系统的层次架构** ⭕ 必背（层次归属题）
  教材图 4-1「信息系统层次架构」**从上往下三层**：
  | 层 | 内容 |
  |---|---|
  | 最上层 | **管理** |
  | 中间层 | **信息系统** |
  | 最下层 | **人员 · 技术 · 流程 · 数据**（四要素） |
  - 在层次架构中，**信息系统之上是「管理」**，它**监督系统的设计和结构**，并**监控其整体性能**
  - 层次架构的作用：提供一个**蓝图**，可以将**业务和系统策略转换为组件或基础架构**，并以恰当的**人员、技术、流程和数据**组合加以实现
  > 记法：**管理管系统，系统由四要素搭**；「监督设计和结构 · 监控整体性能」是**管理**层动词（不是信息系统层）
- [ ] **A2 · 信息系统管理覆盖四大领域** ⭕ 必考（教材 P94 原文定义）
  | 领域 | 教材定义（落点） |
  |---|---|
  | **规划和组织** | 针对信息系统的**整体组织、战略和支持活动** |
  | **设计和实施** | 针对信息系统解决方案的**定义、采购和实施**，以及**它们与业务流程的整合** |
  | **运维和服务** | 针对信息系统**服务的运行交付和支持**，**包括安全** |
  | **优化和持续改进** | 针对信息系统**性能监控**及其于**内部性能目标、内部控制目标和外部要求**的一致性管理 |
  > 口诀：**规设运优**（规划组织 · 设计实施 · 运维服务 · 优化改进）。辨析落点：**设计 = 定义 / 采购 / 实施 / 与业务流程整合**（别与「优化」的一致性管理对调）
- [ ] **A3 · 系统管理的必要性（信息系统的「双面性」）** ⭕ 常考
  信息系统的发展和应用带来极大便利和效益，但同时也带来**诸多风险和挑战**（如**网络安全、数据泄露、个人隐私保护**）。因此，信息系统管理需要：
  - 加强对信息系统的**规范管理和监督**
  - 注重**平衡不同利益干系人之间的关系**
  - 实现信息系统的**良性互动和可持续发展**
  > 记法：一面是**创新引擎**（支撑大数据 / AI / 物联网），一面是**风险载体**（网络安全 / 隐私泄露）——两句话概括「为什么要管」

### 模块 B ｜ 规划和组织（4.1.2）

- [ ] **B0 · 规划模型：信息系统战略三角** ⭕ 必背（本节最核心的一张图）
  - **规划和组织的前提**：需要根据组织的**发展目标**和其他相关因素，规划信息系统的**战略、组成、建设、运行和运营**等；目标是**通过实施具备一致性的管理方法，满足业务对信息系统的管理需求**
  - **信息系统战略三角**：突出**业务战略、信息系统和组织机制**之间的**必要一致性**（教材图 4-2）。它用于描述**信息系统与业务系统必要的协同关系**，以及**理解信息系统与组织机制间的相互影响**
  - 核心句：**成功的组织有一个压倒一切的业务战略，可以推动组织机制和信息系统的有机融合**
  - 战略概念：**战略**是实现目标、意图和目的的一组协调行动；**战略往往始于使命**，而**使命**是对组织的宗旨给出的一个清晰并令人信服的陈述
  - 组织需要**平衡**信息系统战略三角，注重**动态调整**，并考虑三者之间的相互影响
  > 记法：三角三边「**业务战略 · 信息系统 · 组织机制**」；「压倒一切」修饰的是**业务战略**（业务战略是核心）
- [ ] **B1 · 组织模型（1）业务战略：波特竞争力优势模型** ⭕ 必背（三战略年年考）
  | 战略 | 要点 |
  |---|---|
  | **总成本领先战略** | 组织目标是成为市场上**成本最低的生产者**；通过**最大限度地降低成本**获得**高于平均水平的绩效**；产品或服务必须在**质量上与业内相当**（让客户感知相对高性价比）；通常一个行业中**只存在一个成本引领者** |
  | **差异性战略** | 通过差异化，以一种在市场上显得**独特**的方式，**定义其产品或服务**；组织确定哪些**定性维度**对客户最重要，然后在其中一个或多个维度**增加产品和服务的价值**；为使策略奏效，**差异化因素收取的价格必须相对竞争对手是公平的** |
  | **专注战略** | 允许组织将范围**限制在更狭窄的细分市场**，并为该组客户**量身定制**其产品；两种变体：①**专注成本**（在细分市场内寻求成本优势）；②**专注差异化**（寻求细分市场内的产品或服务差异化）；可实现**区域竞争优势**（即局部竞争优势） |
  > 口径提醒：教材原文用词是「**差异性**战略」「**专注**战略」（部分教辅写「差异化 / 专注化」，考试按教材）；「**一个行业只存在一个成本引领者**」挂在总成本领先战略
- [ ] **B2 · 组织模型（2）组织机制战略：莱维特钻石模型** ⭕ 必背（四要素高频挖空）
  - **组织机制战略**本质上需要回答「**组织将如何构建以实现其目标并实施其业务战略**」这个问题
  - **莱维特钻石模型（Leavitt's Diamond）**四要素：**任务 · 结构 · 信息与控制 · 人员**
    | 要素 | 含义 |
    |---|---|
    | **任务** | 核心业务流程和工作内容 |
    | **结构** | 组织架构（部门设置、汇报关系） |
    | **信息与控制** | 数据流转、绩效监控、激励机制 |
    | **人员** | 员工的技能、经验和分工 |
  - 组织机制战略主要涉及组织的**设计、工作流程的控制和文化的变量**的最佳组合；为执行成功的组织机制战略，管理人员应使用该框架**评估当前组织**并确定**哪些组件可能缺失**以及未来的可选项
  > 口诀：**任务 · 结构 · 信息与控制 · 人员**（「莱维特钻石，信息人员结构任务」）。四要素相互影响，单改一个往往落不了地
- [ ] **B3 · 组织模型（3）信息系统战略：矩阵框架** ⭕ 必背
  - **信息系统战略**是组织用来**提供信息服务的计划**；**信息系统支撑组织实施其业务战略**
  - **矩阵框架**用来理解组织必须做出的**与信息系统相关的决策**，核心是明确四大基础结构组件的**「有什么 · 谁使用 · 在哪里」**
  - **四大基础结构**：**硬件 · 软件 · 网络 · 数据**
    | 组件 | 示例 | 要明确什么 |
    |---|---|---|
    | **硬件** | 服务器、终端 | 用户 / 部署位置（云端或数据中心） |
    | **软件** | ERP、办公软件 | 使用部门 / 运行载体 |
    | **网络** | 光纤、无线网络 | 接入人员 / 覆盖范围 |
    | **数据** | 客户数据、交易记录 | 所有者 / 管理者 / 存储位置 |
  > 记法：信息系统战略三问 =「**有什么 · 谁使用 · 在哪里**」；四大基础结构「**硬软网数**」。⚠️ 别与 B2 的钻石四要素（任务/结构/信息与控制/人员）混——两套「四要素」分属**组织机制战略**与**信息系统战略**
- [ ] **B4 · 组织模型总览（三个子模型归属）** ⭕ 常考（归属辨析）
  | 子模型 | 理论 / 工具 | 关键内容 |
  |---|---|---|
  | **业务战略** | **波特竞争力优势模型** | 总成本领先 / 差异性 / 专注 |
  | **组织机制战略** | **莱维特钻石模型** | 任务 / 结构 / 信息与控制 / 人员 |
  | **信息系统战略** | **矩阵框架** | 硬件 / 软件 / 网络 / 数据 |
  > 记法：**业务看波特 · 组织看莱维特 · 信息系统看矩阵**——「模型名 ⇄ 内容」一一配对是本节最爱出的题

### 模块 C ｜ 设计和实施（4.1.3）

- [ ] **C0 · 设计方法（三步转换）** ⭕ 必背
  开展信息系统设计和实施，首先需要**将业务需求转换为信息系统架构**——信息系统架构为**将组织业务战略转换为信息系统的计划**提供了**蓝图**。
  | 步骤 | 内容 |
  |---|---|
  | **① 从战略到系统架构** | 业务战略 →（更具体的）**目标** → **业务需求** → 转换为构成信息系统架构的**系统要求、标准和流程**的更详细**视图**（含考虑数据和流程需求、安全目标、治理安排、权责） |
  | **② 从系统架构到系统设计** | 将**信息系统架构转换为系统设计**：继承架构并**添加更多细节**，包括实际的**硬件、数据、网络和软件** |
  | **③ 转换框架** | 将**业务战略**转化为**信息系统架构**，进而转变为**信息系统设计**；提出**三类问题：内容 · 人员 · 位置**，需要为每个信息系统组件回答这些问题 |
  - **转换框架三类问题**的展开：
    - **内容**（最常被问到）：需要回答**组件是什么**，并确定**特定类型的技术**等
    - **人员**：旨在了解相关组件**涉及哪些个人、团体和部门**（注意：单个用户并非系统的所有者；系统也可能由组织**租赁**而非拥有，所有者成为组织的**外部一方**）
    - **位置（何处）**：随着网络激增，许多信息系统的设计和构建可能**跨越多个位置**使用组件——了解信息系统意味着需要**了解所有内容各自的位置**
  > 口诀：**战略 → 架构 → 设计**（三步递进）；转换框架三问「**内容 · 人员 · 位置**」。⚠️「业务需求转架构」是第①步、「架构转设计」是第②步，箭头方向别接反
- [ ] **C1 · 信息系统具有三个级别** ⭕ 常考（级别归属）
  | 级别 | 内容 |
  |---|---|
  | **全局级别** | 可能侧重于**整个组织**，并构成**整个组织的信息环境** |
  | **组织间级别** | 为**跨组织边界**的服务对象、供应商或其他利益干系人的**沟通交流**奠定基础 |
  | **应用级** | 在考虑**特定业务应用**时，通常重点考虑**数据库和程序组件**，以及它们**运行的设备和操作环境** |
  > 记法：**全局（组织内）→ 组织间（跨边界）→ 应用级（单个应用）**。三级别出现在「从系统架构到系统设计」的展开里
- [ ] **C2 · 架构模式（三种常见模式）** ⭕ 必背（别称 + 适用场景是高频）
  教材表 4-3「信息系统体系架构有三种常见模式」：
  | 架构模式 | 描述 | **别称术语** | 什么时候使用 |
  |---|---|---|---|
  | **集中式架构** | 大型中央计算机系统处理系统的**所有功能**，通常位于**数据中心**，由 **IT 部门直接管理**；存储的数据和应用程序都运行于中央计算机 | **主机架构** | 当需要系统**易于管理**时；**所有功能都在同一个地方**；**业务本身高度集中**的时候 |
  | **分布式架构** | 运行业务所需的**计算能力分散在许多设备中**（不同位置的服务器、PC、笔记本、智能手机、平板）；设备（客户端）具有**足够的处理能力**执行许多服务，并**按需连接中央服务器** | **基于服务器的架构** | 当**担心可伸缩性**时（**模块化**在这里有帮助）；当**业务主要是非集中化**的时候 |
  | **面向服务的系统架构（SOA）** | 在被称为**编排**的过程中，将较大的软件程序**分解为相互连接的服务**，共同构成一个**应用**来运行整个业务流程；服务可从**互联网上的一系列供应商**处获得，应用则是这些服务链接在一起形成的**组合** | **基于 Web 的架构** | 当希望系统成为**敏捷架构**：**可重用性和组件化**利于创造新应用；业务对**新应用和快速设计迭代**要求较高时 |
  - **集中式 vs 分布式的权衡**：**分布式**比集中式**更加模块化**，允许相对容易地**添加其他服务器**，并能为特定用户添加**具有特定功能的客户端**，从而提供更大的**灵活性和多中心化的组织治理机制**（可能令架构决策与组织治理目标更协调）；相比之下**集中式**在某些方面**更易于管理**，因为所有功能都集中在**主机或小型机**中，而不是分布在所有设备和服务器中
  > 口诀：**集中式易管理 · 分布式可扩展 · SOA 更敏捷**。⚠️ **「基于 Web 的架构」是 SOA 的别称，不是第四种模式**（三模式别记成四个）；「主机架构」= 集中式、「基于服务器的架构」= 分布式

### 模块 D ｜ 运维和服务（4.1.4）

- [ ] **D0 · 运维和服务八项活动总览** ⭕ 必背（清单题）
  信息系统的运维和服务应从**信息系统运行的视角**进行**整合性的统筹规划**，包括对信息系统、应用程序和基础设施的**日常控制**进行综合管理。由各类管理活动组成，**主要包括八项**：
  | # | 活动 |
  |---|---|
  | 1 | **运行管理和控制** |
  | 2 | **IT 服务管理** |
  | 3 | **运行与监控** |
  | 4 | **终端侧管理** |
  | 5 | **程序库管理** |
  | 6 | **安全管理** |
  | 7 | **介质控制** |
  | 8 | **数据管理** |
  > 记法：**运服监终程安介数**（前三项是重点，后五项只考归属）
- [ ] **D1 · 运行管理和控制（四活动）** ⭕ 必背
  | 活动 | 要点 |
  |---|---|
  | **过程开发** | 操作人员执行的**重复性活动**应以**过程的形式**记录下来；需**开发、审查和批准**描述每个过程及其每个步骤的相关**文档**，并提供给运营人员 |
  | **标准制定** | 从**运行执行任务的方式**到**所使用的技术**，采用**标准化定义和约束** |
  | **资源分配** | 管理层分配支持信息系统运行的各项能力，包括**人力、技术和资源** |
  | **过程管理** | **测量和管理**所有信息系统运行的相关过程，确保过程在**时间上和预算目标内**被**正确和准确地执行** |
  > 口诀：**过程开发 + 标准制定 + 资源分配 + 过程管理**（「过程开发加标准，资源分配过程管」）
- [ ] **D2 · IT 服务管理（11 项）** ⭕ 必背（数字型高频）
  IT 服务管理是**通过主动管理和流程的持续改进来确保 IT 服务交付有效且高效**的一组活动。由若干不同的活动组成：
  | # | 活动 | 一句话抓住它 |
  |---|---|---|
  | 1 | **服务台** | 用户接口 / 单一联系点，负责事件响应与需求受理 |
  | 2 | **事件管理** | 处理**计划外的服务中断或质量下降**，核心是**快速恢复服务** |
  | 3 | **问题管理** | 针对**重复出现的同类事件**做**根因分析**，防止复发 |
  | 4 | **变更管理** | 管控变更（软件升级 / 硬件更换），**降低变更风险** |
  | 5 | **配置管理** | 记录**配置项及相互关系**（**CMDB**） |
  | 6 | **发布管理** | 规划并实施**发布**（新版本上线），保护现有运营环境 |
  | 7 | **服务级别管理** | 通过 **SLA** 明确服务标准并监控改进 |
  | 8 | **财务管理** | 预算、费用、**投资回报率 ROI** |
  | 9 | **容量管理** | 确保资源满足**当前和未来需求** |
  | 10 | **服务连续性管理** | 灾难恢复计划，确保灾难时**快速恢复服务** |
  | 11 | **可用性管理** | 监控和提升**系统可用程度**（约定时段内可使用比例） |
  > 记法：**共 11 项**。别混：**事件管理 = 快速恢复**（治标）↔ **问题管理 = 根因/防复发**（治本）；**容量**管资源够不够、**可用性**管能不能用、**连续性**管灾后能不能恢复
- [ ] **D3 · 运行与监控（两类任务）** ⭕ 常考
  - **① 运行任务**（有效的 IT 运行要求 IT 人员按既定流程正确执行任务），常包括**6 条**：
    1. **按照计划执行作业**
    2. **监控作业**，并**按照优先级**为作业分配资源
    3. **重新启动失败的作业和进程**
    4. 通过**加载或变更备份介质**，或通过确保**目标的存储系统就绪**来**优化备份作业**
    5. **监控信息系统、应用程序和网络的可用性**，保证这些系统具备**足够的性能**
    6. 实施**空闲期的维护活动**，如**设备清洁和系统重启**等
  - **② 监控任务**：**运行监控** · **安全监控**
    - IT 团队应对信息系统、应用程序和基础设施进行监控，确保它们**继续按要求运行**；检测和报告的错误类型包括**系统错误、程序错误、通信错误和操作员错误**
    - **安全监控**是整体策略的一部分，用于**预防和响应安全事件**；监控类型包括：防火墙策略规则中的例外情况、入侵防御系统的告警、数据丢失防护系统的告警、云安全访问代理的告警、用户访问管理系统的告警、网络异常的告警、网页内容过滤系统的告警、终端管理系统的告警（含反恶意软件）、供应商发布的安全公告、第三方发布的安全公告、威胁情报咨询、门禁系统的告警、视频监控系统的告警等
  > 记法：**运行任务 6 条 + 监控任务 2 类（运行监控 / 安全监控）**；**错误四类「系程通操」**
- [ ] **D4 · 其余五项：终端侧 / 程序库 / 安全 / 介质 / 数据** ⭕ 了解（只考归属）
  - **终端侧管理**、**安全管理**、**数据管理**（数据管理详见 4.2.1）
  - **程序库管理**：应用程序代码可能包含**算法、加密密钥和其他敏感信息**，应视为**信息**，受组织的**安全策略和数据分类策略**管理；控制程序库可使组织高度控制其应用程序的**完整性、质量和安全性**；程序库通常作为**信息系统**存在，具有用户界面和多种功能，主要包括**访问控制 · 程序签出 · 程序签入 · 版本控制 · 代码分析**
  - **介质控制**：处置**不再需要的介质**相关的程序，包括**擦除介质上的数据**或使数据**无法以其他方式恢复**的所有相关步骤；需要考虑的介质主要包括**备份介质、虚拟磁带库、光学介质、硬盘驱动器、固态驱动器、闪存、硬拷贝**等；介质清理的策略和程序需要包含在**服务提供商的相关要求**中，以及**记录保存活动**以跟踪介质随时间推移的销毁情况
  > 记法：程序库五功能「**访签出签入版分**」（访问控制 / 签出 / 签入 / 版本控制 / 代码分析）

### 模块 E ｜ 优化和持续改进（4.1.5）

- [ ] **E0 · 传统方法：戴明环 PDCA** ⭕ 必背
  优化和持续改进是信息系统管理活动中的一个环节，良好的管理活动能有效保障信息系统的**性能和可用性**等，**延长整体系统的有效使用周期**。传统上常用方法为**戴明环，即 PDCA 循环**，将持续改进分为**四个阶段**：
  | 阶段 | 英文 |
  |---|---|
  | **计划** | Plan |
  | **执行** | Do |
  | **检查** | Check |
  | **处理** | Act |
  > 记法：**P 计划 · D 执行 · C 检查 · A 处理**
- [ ] **E1 · 六西格玛五阶段：DMAIC / DMADV** ⭕ 必背（转化关系是高频）
  - 优化和持续改进**基于有效的变更管理**，使用**六西格玛倡导的五阶段方法 DMAIC/DMADV**，是对**戴明环四阶段周期的延伸**，包括：**定义（Define）· 度量（Measure）· 分析（Analysis）· 改进/设计（Improve/Design）· 控制/验证（Control/Verify）**
  - **转化关系**：当第四阶段的「**改进**」替换为「**设计**」、第五阶段的「**控制**」替换为「**验证**」时，五阶段法就从 **DMAIC** 转变为 **DMADV**
  - **适用区别**：**DMAIC** 帮助组织**识别和消除导致产品或过程缺陷的根本原因**，适用于**现有过程/流程的改进**；**DMADV** 用于**设计新的产品或过程**
  > 记法：五阶段「**定度分改控**」；**DMAIC 改现有 · DMADV 设新的**；替换只在**第 4、5 阶段**（改进→设计、控制→验证）
- [ ] **E2 · 定义阶段（三目标）** ⭕ 必背
  | 目标 | 要点 |
  |---|---|
  | **待优化信息系统定义** | 关注确定**待优化信息系统的范围、优化目标和目的、系统团队成员和出资人，以及优化时间表和交付成果**；可使用「**延伸目标**」概念来定义待优化的信息系统，帮助**超越渐进式改进**、重新思考信息系统相关业务 |
  | **核心流程定义** | 关注定义**利益干系人、投入和产出以及广泛的功能**；**SIPOC 分析**（**供方 Supplier、输入 Input、流程 Process、输出 Output、服务对象 Customer**）是**定义核心流程视图的首选工具** |
  | **团队组建** | 关注确定**高能力团队**，对信息系统的问题和收益**达成共识**；通常由 **5~7 名核心成员**组成，其他成员可能是来自**非关键利益干系人组的临时成员**（仅在需要时参与） |
  > 记法：定义阶段三目标「**系统定义 · 核心流程 · 团队组建**」；**SIPOC = 首选工具**（别答成价值流分析，那是分析阶段）；团队规模 **5~7 名核心成员**
- [ ] **E3 · 度量阶段（四目标 + 度量系统五特性）** ⭕ 必考
  - **度量阶段目标包括四项**：**流程定义 · 指标定义 · 流程基线 · 度量系统分析**
  - 关键句：**质量始于度量**——只有当**质量被量化时**，才能开始讨论优化和持续改进
  - **一个良好的度量系统具备的特性可包括**：**准确 · 可重复 · 线性 · 可重现 · 稳定**
  > 口诀：度量四目标「**流定指基度量析**」；度量系统五特性「**准重线现稳**」（注意是「**可重复**」和「**可重现**」两个都在，别合并）
- [ ] **E4 · 分析阶段（三目标）** ⭕ 常考
  分析阶段的三个目标包括：
  1. **价值流分析**
  2. **信息系统异常的源头分析**
  3. **确定优化改进的驱动因素**
  > 记法：分析三目标「**价值流 · 异常源头 · 改进驱动因素**」；**价值流分析**只在分析阶段出现
- [ ] **E5 · 改进/设计阶段与控制/验证阶段** ⭕ 常考
  - **改进/设计阶段**目标：①向**发起人**提出一个或多个**解决方案**，**量化每种方法的收益**，就解决方案**达成共识并实施**；②**定义新的操作/设计条件**；③为新工艺/设计提供**定义和缓解故障模式**
  - **控制/验证阶段**目标：①**标准化**新程序/新系统功能的**操作控制要素**；②**持续验证**优化的信息系统的**可交付成果**；③**记录经验教训**
  > 记法：改进/设计 = **提方案 · 量化收益 · 定新条件 · 缓解故障模式**；控制/验证 = **标准化 · 持续验证 · 记经验教训**（「记录经验教训」在**最后一阶段**）

<summary>参考答案（先自己答完再展开）</summary>

1. 信息系统是对信息进行**采集、处理、存储、管理和检索**，形成组织中的信息流动和处理，必要时能向有关人员提供有用信息的系统，是由**人、技术、流程和数据资源**组成的**人机系统**。四要素：**人员 · 技术 · 流程 · 数据**
2. 从下往上三层为「**人员/技术/流程/数据**（四要素）→ **信息系统** → **管理**」（正文表述为：信息系统之上是管理）。「**监督系统的设计和结构 · 监控其整体性能**」是**管理**层的职责
3. ①**规划和组织**（整体组织、战略和支持活动）；②**设计和实施**（解决方案的**定义、采购和实施**，以及**与业务流程的整合**）；③**运维和服务**（服务的**运行交付和支持**，**包括安全**）；④**优化和持续改进**（**性能监控**及其于**内部性能目标、内部控制目标和外部要求**的一致性管理）
4. 因为信息系统有「**双面性**」：一面是**创新引擎**（支撑大数据、AI、物联网），一面是**风险载体**（**网络安全、数据泄露、个人隐私保护**等风险挑战）。系统管理要：加强对信息系统的**规范管理和监督**；注重**平衡不同利益干系人之间的关系**；实现**良性互动和可持续发展**
5. 需要根据组织的**发展目标**和其他相关因素，规划信息系统的**战略、组成、建设、运行和运营**等。目标是通过实施具备**一致性**的管理方法，**满足业务对信息系统的管理需求**
6. **业务战略 · 信息系统 · 组织机制**。「压倒一切」修饰的是**业务战略**（成功的组织有一个压倒一切的业务战略，可推动组织机制和信息系统的有机融合）。三角用于描述**信息系统与业务系统必要的协同关系**，以及理解**信息系统与组织机制间的相互影响**
7. **总成本领先战略 · 差异性战略 · 专注战略**。「一个行业中只存在一个成本引领者」说的是**总成本领先战略**
8. **①专注成本**（在细分市场内寻求成本优势）；**②专注差异化**（寻求细分市场内的产品或服务差异化）。可实现**区域竞争优势**（局部竞争优势）
9. **任务 · 结构 · 信息与控制 · 人员**。组织机制战略本质上需要回答「**组织将如何构建以实现其目标并实施其业务战略**」
10. **信息系统战略**是组织用来**提供信息服务的计划**（信息系统支撑组织实施其业务战略）。四大基础结构：**硬件 · 软件 · 网络 · 数据**。三问：**有什么 · 谁使用 · 在哪里**
11. **业务战略 ⇄ 波特竞争力优势模型**（总成本领先 / 差异性 / 专注）；**组织机制战略 ⇄ 莱维特钻石模型**（任务 / 结构 / 信息与控制 / 人员）；**信息系统战略 ⇄ 矩阵框架**（硬件 / 软件 / 网络 / 数据）
12. 首先需要**将业务需求转换为信息系统架构**。信息系统架构为**将组织业务战略转换为信息系统的计划**提供了**蓝图**
13. **①从战略到系统架构 ②从系统架构到系统设计 ③转换框架**。「从战略到系统架构」链条：**业务战略 → 更具体的目标 → 业务需求 → 转换为构成信息系统架构的系统要求、标准和流程的更详细视图**
14. **全局级别**（侧重整个组织，构成整个组织的信息环境）；**组织间级别**（为跨组织边界的服务对象、供应商或其他利益干系人的沟通交流奠定基础）；**应用级**（考虑特定业务应用时重点考虑的数据库和程序组件，以及它们运行的设备和操作环境）
15. **内容 · 人员 · 位置**。「**内容**」相关问题**最常被问到**（回答组件是什么、确定特定类型的技术）。「人员」旨在了解相关组件**涉及哪些个人、团体和部门**——注意单个用户并非系统的所有者；系统也可能由组织**租赁**而非拥有，此时所有者成为组织的**外部一方**
16. **①集中式架构**（别称**主机架构**：需要系统易于管理、所有功能都在同一个地方、业务本身高度集中时）；**②分布式架构**（别称**基于服务器的架构**：担心可伸缩性、模块化有帮助、业务主要是非集中化时）；**③面向服务的系统架构 SOA**（别称**基于 Web 的架构**：希望系统成为敏捷架构、可重用性和组件化、对新应用和快速设计迭代要求较高时）
17. **分布式**比集中式更**模块化**，允许相对容易地**添加其他服务器**，能为特定用户添加特定功能的客户端，提供更大的**灵活性和多中心化的组织治理机制**（可能与组织治理目标更协调）；**集中式**在某些方面**更易于管理**，因为所有功能都集中在**主机或小型机**中，而非分布在所有设备和服务器中
18. **运行管理和控制 · IT 服务管理 · 运行与监控 · 终端侧管理 · 程序库管理 · 安全管理 · 介质控制 · 数据管理**
19. **过程开发 · 标准制定 · 资源分配 · 过程管理**。过程管理要确保过程在**时间上和预算目标内**被**正确和准确地执行**
20. **服务台 · 事件管理 · 问题管理 · 变更管理 · 配置管理 · 发布管理 · 服务级别管理 · 财务管理 · 容量管理 · 服务连续性管理 · 可用性管理**（共 11 项）。区别：**事件管理**处理计划外的服务中断或质量下降，核心是**快速恢复服务**（治标）；**问题管理**针对**重复出现的同类事件**做**根因分析**、防止复发（治本）
21. 运行任务（6 条）：①按照计划执行作业；②监控作业并按优先级分配资源；③重新启动失败的作业和进程；④通过加载或变更备份介质、或确保目标的存储系统就绪来优化备份作业；⑤监控信息系统、应用程序和网络的可用性，保证足够性能；⑥实施空闲期的维护活动（设备清洁和系统重启等）。错误类型四类：**系统错误 · 程序错误 · 通信错误 · 操作员错误**。监控任务两类：**运行监控 · 安全监控**
22. 传统方法 = **戴明环 PDCA**（**计划 Plan · 执行 Do · 检查 Check · 处理 Act**）。五阶段 = **定义 Define · 度量 Measure · 分析 Analysis · 改进/设计 Improve/Design · 控制/验证 Control/Verify**；当第 4 阶段「改进」替换为「设计」、第 5 阶段「控制」替换为「验证」时 **DMAIC → DMADV**；**DMAIC 适用于现有过程的改进，DMADV 用于设计新的产品或过程**。定义阶段三目标：**待优化信息系统定义 · 核心流程定义 · 团队组建**；度量阶段四目标：**流程定义 · 指标定义 · 流程基线 · 度量系统分析**；良好度量系统五特性：**准确 · 可重复 · 线性 · 可重现 · 稳定**

</details>
