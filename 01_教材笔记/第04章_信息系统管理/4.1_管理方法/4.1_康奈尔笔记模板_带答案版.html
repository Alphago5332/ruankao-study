4.1.1 管理基础
1信息系统的定义、四要素与层次架构
  • 定义：信息系统是对信息进行采集、处理、存储、管理和检索，形成组织中的信息流动和处理，必要时能向有关人员提供有用信息的系统，是由人、技术、流程和数据资源组成的人机系统
  • 四大要素：人员（使用者 / 管理者 / 开发者）· 技术（硬件 / 软件 / 网络）· 流程（管理流程 / 业务流程）· 数据（信息载体 / 决策依据）
  • 层次架构（图 4-1，从下往上）：人员 · 技术 · 流程 · 数据 → 信息系统 → 管理；在层次架构中信息系统之上是「管理」
  • 管理层的动词：监督系统的设计和结构，并监控其整体性能
口诀：定义抓五动词「采处存管检」；四要素「人技流数」；「监督 + 监控」属管理层（不是信息系统层）
2四大管理领域（教材 P94 原文落点）
  • 规划和组织：针对信息系统的整体组织、战略和支持活动
  • 设计和实施：针对信息系统解决方案的定义、采购和实施，以及它们与业务流程的整合
  • 运维和服务：针对信息系统服务的运行交付和支持，包括安全
  • 优化和持续改进：针对信息系统性能监控及其于内部性能目标、内部控制目标和外部要求的一致性管理
口诀 规设运优。⚠️ 包含「采购」二字的是设计和实施；出现「一致性管理」的是优化和持续改进——四个领域最爱互相调包
3系统管理的必要性与「双面性」
  • 双面性：一面是创新引擎（支撑大数据、AI、物联网等应用），一面是风险载体（网络安全、数据泄露、个人隐私保护等风险挑战）
  • 因此要：①加强对信息系统的规范管理和监督；②注重平衡不同利益干系人之间的关系；③实现信息系统的良性互动和可持续发展
记法：创新引擎 + 风险载体两句定性，正是「为什么要做信息系统管理」的答案；三个「要」是它落地的方向
4.1.2 规划和组织
4规划模型：信息系统战略三角
  • 前提：根据组织的发展目标和其他相关因素，规划信息系统的战略、组成、建设、运行和运营；目标是通过实施具备一致性的管理方法，满足业务对信息系统的管理需求
  • 战略三角（图 4-2）：业务战略 · 信息系统 · 组织机制，突出三者之间的必要一致性；用于描述信息系统与业务系统必要的协同关系，以及理解信息系统与组织机制间的相互影响
  • 核心句：成功的组织有一个压倒一切的「业务战略」，可以推动组织机制和信息系统的有机融合
  • 战略 / 使命：战略是实现目标、意图和目的的一组协调行动；战略往往始于使命，使命是对组织的宗旨给出的清晰并令人信服的陈述
三角三边「业务战略 · 信息系统 · 组织机制」；「压倒一切」修饰业务战略（不是组织机制）；三者需动态调整而非静态协同
5组织模型（1）业务战略：波特竞争力优势模型
  • 总成本领先战略：成为市场上成本最低的生产者；最大限度降低成本→获得高于平均水平的绩效；质量须与业内相当（客户感知高性价比）；一个行业中只存在一个成本引领者
  • 差异性战略：以在市场上显得独特的方式定义其产品或服务；确定对客户最重要的定性维度并增加价值；收取的价格相对竞争对手必须公平
  • 专注战略：将范围限制在更狭窄的细分市场并量身定制；两种变体 = ①专注成本 ②专注差异化；可实现区域竞争优势
教材原文用词是「差异性战略」「专注战略」（教辅常写差异化 / 专注化，按教材）；「一个行业只存在一个成本引领者」挂总成本领先
6组织模型（2）(3)：莱维特钻石模型 + 信息系统战略
组织机制战略 · 莱维特钻石模型
  • 本质要回答：组织将如何构建以实现其目标并实施其业务战略
  • 四要素：任务（核心业务流程与工作内容）· 结构（组织架构 / 部门与汇报关系）· 信息与控制（数据流转 / 绩效监控 / 激励机制）· 人员（技能 / 经验 / 分工）
信息系统战略 · 矩阵框架
  • 信息系统战略是组织用来提供信息服务的计划；信息系统支撑组织实施其业务战略
  • 四大基础结构：硬件 · 软件 · 网络 · 数据
  • 三问：有什么 · 谁使用 · 在哪里
⚠️ 两套「四要素」别混：组织机制战略 = 钻石「任务 / 结构 / 信息与控制 / 人员」；信息系统战略 = 矩阵「硬件 / 软件 / 网络 / 数据」。配对口诀「业务看波特 · 组织看莱维特 · 信息系统看矩阵」
4.1.3 设计和实施
7设计方法（三步转换）+ 转换框架
  • 前置：首先需要将业务需求转换为信息系统架构——架构为将组织业务战略转换为信息系统的计划提供蓝图
  • ① 从战略到系统架构：业务战略 → 更具体的目标 → 业务需求 → 转换为构成信息系统架构的系统要求、标准和流程的更详细视图
  • ② 从系统架构到系统设计：将架构转为系统设计（继承架构 + 添加细节：实际的硬件、数据、网络和软件）
  • ③ 转换框架：将业务战略→信息系统架构→信息系统设计；提出三类问题，需为每个组件回答
转换框架三类问题
  • 内容（最常被问到）：回答组件是什么，确定特定类型的技术
  • 人员：了解相关组件涉及哪些个人、团体和部门（单个用户常非系统所有者；系统也可能被租赁，所有者成为组织的外部一方）
  • 位置（何处）：把所有内容各自的位置弄清楚（组件可能跨越多个位置）
口诀：战略 → 架构 → 设计（箭头方向别接反）；转换框架三问「内容 · 人员 · 位置」，内容最常被问到
8信息系统三级别 + 三种架构模式
信息系统三个级别
  • 全局级别：侧重整个组织，构成整个组织的信息环境
  • 组织间级别：为跨组织边界的服务对象、供应商或其他利益干系人的沟通交流奠定基础
  • 应用级：考虑特定业务应用时重点考虑的数据库和程序组件，以及它们运行的设备和操作环境
三种架构模式（表 4-3）
  • 集中式架构（别称 主机架构）：大型中央计算机处理所有功能，通常位于数据中心，由 IT 部门直接管理；用于需要系统易于管理 / 所有功能在同一个地方 / 业务本身高度集中时
  • 分布式架构（别称 基于服务器的架构）：计算能力分散在许多设备（服务器 / PC / 笔记本 / 智能手机 / 平板），设备有足够处理能力执行多数服务、按需连接中央服务器；用于担心可伸缩性（模块化有帮助）/ 业务主要是非集中化时
  • 面向服务的系统架构 SOA（别称 基于 Web 的架构）：在被称为编排的过程中把较大软件程序分解为相互连接的服务，共同构成一个应用运行整个业务流程；服务可从互联网供应商处获得；用于希望系统成为敏捷架构 / 可重用性和组件化 / 对新应用和快速设计迭代要求较高时
集中式 vs 分布的权衡
  • 分布式更模块化，允许相对容易地添加服务器、为特定用户添加特定功能的客户端，提供更大的灵活性和多中心化的组织治理机制（可能令架构决策与治理目标更协调）
  • 集中式在某些方面更易于管理，因为所有功能都在主机或小型机中，而非分布在所有设备和服务器中
口诀 集中式易管理 · 分布式可扩展 · SOA 更敏捷。⚠️ 「基于 Web 的架构」是 SOA 的别称，不是第四种模式；「主机架构」= 集中式、「基于服务器的架构」= 分布式
4.1.4 运维和服务
9运维和服务八项活动 + 运行管理和控制
  • 八项活动：运行管理和控制 · IT 服务管理 · 运行与监控 · 终端侧管理 · 程序库管理 · 安全管理 · 介质控制 · 数据管理
  • 运行管理和控制四活动：
四活动要点
  • 过程开发：重复性活动应以过程形式记录下来；需开发、审查和批准描述每个过程及其步骤的文档并提供给运营人员
  • 标准制定：从运行执行任务的方式到所使用的技术，采用标准化定义和约束
  • 资源分配：管理层分配支持系统运行的各项能力，包括人力、技术和资源
  • 过程管理：测量和管理所有运行相关过程，确保过程在时间上和预算目标内被正确和准确地执行
口诀：过程开发加标准，资源分配过程管；八项串记「运服监终程安介数」（前三项是重点）
10IT 服务管理 + 运行与监控
IT 服务管理（11 项）
  • 服务台 · 事件管理 · 问题管理 · 变更管理 · 配置管理 · 发布管理 · 服务级别管理 · 财务管理 · 容量管理 · 服务连续性管理 · 可用性管理
  • 关键辨识：事件管理 = 快速恢复服务（治标）；问题管理 = 根因分析、防复发（治本）；配置管理管配置项与关系（CMDB）；服务级别管理靠 SLA；容量管资源够不够、可用性管能不能用、连续性管灾后恢复
运行任务（6 条）
  • ①按照计划执行作业 ②监控作业并按优先级分配资源 ③重新启动失败的作业和进程 ④通过加载或变更备份介质、或确保目标的存储系统就绪来优化备份作业 ⑤监控信息系统、应用程序和网络的可用性，保证足够性能 ⑥实施空闲期的维护活动（设备清洁 / 系统重启等）
监控任务（2 类）与错误类型
  • 监控任务：运行监控 · 安全监控（安全监控是整体策略的一部分，用于预防和响应安全事件，覆盖防火墙例外 / 入侵防御告警 / 数据丢失防护 / 用户访问管理 / 终端管理 / 门禁 / 视频监控等）
  • 检测和报告的错误类型：系统错误 · 程序错误 · 通信错误 · 操作员错误
⚠️ 事件（快恢复）↔ 问题（查根因）是最高频的调包点；错误四类口诀「系程通操」
4.1.5 优化和持续改进
11PDCA 与 DMAIC / DMADV
  • 作用定位：优化和持续改进能有效保障信息系统的性能和可用性，延长整体系统的有效使用周期
  • 传统方法：戴明环 PDCA——计划 Plan · 执行 Do · 检查 Check · 处理 Act
  • 五阶段方法：优化和持续改进基于有效的变更管理，使用六西格玛倡导的 DMAIC/DMADV，是对戴明环四阶段周期的延伸——定义 Define · 度量 Measure · 分析 Analysis · 改进/设计 Improve-Design · 控制/验证 Control-Verify
  • 转换关系：第 4 阶段「改进」替换为「设计」、第 5 阶段「控制」替换为「验证」→ DMAIC 变 DMADV
  • 适用场景：DMAIC 用于识别和消除缺陷根本原因，适用现有过程/流程的改进；DMADV 用于设计新的产品或过程
五阶段口诀「定度分改控」；DMAIC 改现有 · DMADV 设新的；替换只发生在第 4、5 阶段
12五阶段目标与度量系统特性
定义阶段（三目标）
  • 待优化信息系统定义：确定范围、优化目标和目的、系统团队成员和出资人、优化时间表和交付成果；可用「延伸目标」概念（帮助超越渐进式改进）
  • 核心流程定义：定义利益干系人、投入和产出以及广泛的功能；SIPOC 分析（供方 / 输入 / 流程 / 输出 / 服务对象）是首选工具
  • 团队组建：确定高能力团队，通常由 5~7 名核心成员组成（另可有非关键干系人组的临时成员）
度量阶段（四目标 + 度量系统五特性）
  • 四目标：流程定义 · 指标定义 · 流程基线 · 度量系统分析；关键句质量始于度量（质量被量化才能谈优化）
  • 良好度量系统特性：准确 · 可重复 · 线性 · 可重现 · 稳定
分析阶段（三目标）
  • 价值流分析 · 信息系统异常的源头分析 · 确定优化改进的驱动因素
改进/设计 · 控制/验证阶段
  • 改进/设计：向发起人提出解决方案并量化收益→达成共识并实施；定义新的操作/设计条件；为新工艺/设计提供定义和缓解故障模式
  • 控制/验证：标准化新程序/新系统的操作控制要素；持续验证优化的可交付成果；记录经验教训
⚠️ SIPOC 属定义阶段、价值流分析属分析阶段（最爱对调）；度量系统五特性「准重线现稳」——可重复与可重现两个都在
总结区 本节本质 + 考点地图
